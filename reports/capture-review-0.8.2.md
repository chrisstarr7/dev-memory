# 记忆漏记审查与修复：0.8.2

日期：2026-10-18。基线为 GitHub `main` 的 `ecc9744`（0.8.1），保留其用户指令 32 KiB 边界修复。本次没有重建 Skill，也没有修改数据库 Schema。

## 发现的原因

| 层次 | 实际发现 | 后果 |
| --- | --- | --- |
| 本机加载 | 实际安装仍为 0.5.2，缺少 Codex 用户级管理块；全局捕获开启，但记录为空 | 拉取仓库不会升级安装，也不会让新项目自动加载 |
| 学习决策 | 旧指令同时要求候选学习，又将“不确定”反馈留在对话中；只给了已确认规则示例 | 首次可复用的方法容易被判成一次性要求，等不到第一条证据 |
| 来源校验 | 推断候选只接受 `user_feedback` | 真实用户要求或选择使用 `user_statement` / `user_confirmation` 时会被拒绝 |
| 证据追加 | 查到已有候选后，AI 可能直接结束，没有写入这次新证据 | 相似记忆被找到，却不能逐渐形成习惯 |
| 可观察性 | 诊断没有安装版本和用户级绑定；旧 `active_count` 混入候选及冲突记录 | 难区分未加载、未写入和已经保存但尚未生效 |

这些是本机可观察事实和合成对话复现，不代表已读取或解释用户在其他宿主中的历史对话。

## 修改

- **首次即可保存候选：**明确的方法、选择、纠错不必等重复。明确跨项目的要求仍直接走已确认规则；没有明确跨项目范围的可复用行为保存为未生效软候选。
- **来源按实际用户表达填写：**支持用户陈述、确认、反馈三类。程序用受控任务哈希计算独立证据；同一任务改变来源类型、反复复述不会增加独立任务数。AI 总结和检索不算用户证据。
- **查重与保存分清：**Skill 和 `match` 回执明确“比较没有保存证据”。等价候选用带版本校验的 `ADD duplicate_of` 追加新来源，不增加正文，由程序判断是否晋升。
- **回执可辨认：**内容和证据写入返回 `memory_status`；不能把候选保存说成已经自动采用。
- **显式诊断：**`doctor` 返回实际 Skill 版本、路径、用户绑定、不同状态的计数。检查当前生效的 override、运行路径、Python 文件及全局根目录；绑定另一个库时明确报告不一致。
- **只启用全局：**新增 `setup --user --agent codex`，不必为了用户习惯初始化业务项目。其他宿主继续使用各自项目适配器。
- **继续守住边界：**一次“这次不测试”、业务状态和项目约束不写全局；候选不进入普通有效规则召回。修复了非 `preference` 类型绕过推断来源预处理的入口。

普通任务仍只需一次有界召回；收尾在主 AI 已有推理中判断增量。没有新证据不调用 `apply`、不输出 NOOP、不启动独立模型或全库整理。新证据需要查重时才进行一次 `match`，随后批量 `apply`。诊断不进入正常热路径。

`python3 -B -m unittest discover -s tests -v`：246 项，37.392 秒，成功；其中 2 项按环境条件跳过。新增 13 项覆盖首次记录、三类来源、同任务不重复计数、查重只读、等价正文追加、独立证据晋升、非用户来源、隐私标记、类型绕过、暂停/单轮跳过、计数及全局激活诊断。

独立只读审查另行复验了不同全局根目录、缺失 Python、match 后不变更证据及显式 apply 晋升。Skill 格式校验、发布包构建通过。程序测试不证明 AI 每次都会遵守指令。

人工复核了实际写入的行为、条件、禁止行为和脱敏来源，检查已有函数是否真的被复用。没有仅靠命令退出码判定成功。最终自动验收谓词也全部通过。

保留了一次失败的中间迭代：第一条候选已保存，但第二个任务只执行 `match`，证据仍为 1。这促成最后的“match 不等于保存”修复。详细聚合与每轮源码哈希见 [宿主结果](capture-host-0.8.2.json)。原始对话和 stderr 不随仓库发布。最终宿主冻结后，运行源码仅修改了发布文件白名单。

首次对照多用 6.675 秒（约 17%）、5 个工具事件；其中记忆命令从一次召回增加为召回、查重、保存三次。不能把所有差异归因于 SQLite，也不能由一次顺序样本推断稳定延迟。此轮未重新做禁用记忆的重复随机对照，没有验证其他宿主或所有模型；新证据的可靠落地确实需要写入成本。

## 数据兼容、本机修复与升级

- Schema 仍为 1；没有历史批量迁移、原文回填、重新归纳或修改旧记忆。已有 SQLite、项目隔离、证据、修订、幂等、备份及遗忘机制保留。旧候选可继续收集有效的新证据，不因升级自动晋升。
- 本机已将托管安装从 0.5.2 升到 0.8.2，并完成仅全局的用户级配置。`doctor` 报告 `user_guided` / configured；捕获与召回开关保持开启。全局配置字节不变，管理块以外的用户指令字节不变；没有初始化业务项目，也没有向真实库导入测试记忆。
- 配置成功不等于宿主执行保证。新会话才能可靠获得更新的 Skill；当前会话可能缓存旧发现元数据。已有会话不会追溯补记过去所有聊天。
- 安全升级：重新运行 README 安装命令；仅有程序安装、希望开启 Codex 跨项目习惯时，用已安装新版 CLI 执行 `setup --user`，然后新建会话。暂停、禁用、只读或单轮隐私控制不会被升级解除。
- 排查用已安装 CLI 的 `doctor`；候选查看 `list --scope global --status candidate`，有效规则查看 `list --scope global --status active`。修正使用带 `expected_revision` 的 `REVISE`；删除使用现有确认式 `forget`。这些不是每轮强制步骤。

无法让纯 Skill 强制每个模型在每轮都调用写入，也无法证明从未提供给它的历史对话含有何种偏好。本次修复针对已复现的加载、首次捕获、来源校验、证据追加和诊断断点。
