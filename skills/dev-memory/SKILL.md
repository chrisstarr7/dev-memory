# dev-memory

Use `python3 <absolute-skill-directory>/scripts/dev_memory.py` as the CLI. Resolve the directory from this loaded SKILL.md; do not assume a shell alias or a fixed host path. This package is independent of other Skills. Installation contains no runtime memories.

## Default activation

A project initialized by `setup` or `install.py --project` has a host-native instruction block and a private `.dev-memory/activation.json` binding. That command is the user's authorization for routine memory in that project. Read the binding and use its runtime/global-root paths. Automatically perform this workflow on ordinary development requests; do not ask for an enable phrase, explicit Skill invocation, or a separate save/continue instruction. Existing capture/read-only/opt-out settings always win. A code-edit limit such as "only modify policy.py" scopes business code changes; the already authorized memory bookkeeping continues unless the user also forbids memory/state writes or all other filesystem changes. An explicit all-files prohibition is respected, never silently bypassed. Plain program installation alone does not activate a project.

Codex can also be explicitly activated at user level with `install.py codex --user` (or `setup --user`). This manages a separate block in `~/.codex/AGENTS.md`, or in `AGENTS.override.md` when that file already controls user instructions. It shares only the global store across projects and never initializes or captures project memory. Other hosts have no user-level adapter unless a host-specific one is documented. If the block, Skill or store is unavailable, report the gap instead of claiming automatic use.

If host IDs are unavailable, generate one opaque local session ID per conversation and one local turn ID per user turn; reuse them for retries. For continuation, use `context --resume --force` to retrieve bounded recent task checkpoint candidates before selecting the continuing task ID (ask only if genuinely ambiguous); create a new task ID only for a genuinely new task.

## Start, recall and apply

1. Load this Skill once per runtime version/conversation context. At task start/resume or a real project/module/topic change, make one bounded `context` call with the actual task terms, project root, stable session ID, known task ID, and `--resume --force` only when continuing. `context` checks storage identity without host probes or initialization. Use `doctor` only for an integration/storage problem; it does not prove that the host loaded this Skill.
2. Shape the query from the work: bug fix → symptom plus debugging, evidence, change scope and regression; feature → requirements, design, code reuse and implementation; review → correctness, risk and requested review focus; build/test/release → verification and delivery. Include the concrete language/module only when it helps distinguish relevant habits. Do not query every category or run a second broad recall to “complete the profile.”
3. Apply the few relevant current rules to the plan, code changes and verification. A habit is guidance, not a substitute for inspecting code. Current user instructions and authoritative project constraints always win, including over confirmed historical habits; inferred soft preferences yield especially readily. Reuse loaded rules while task, topic, workspace and store version remain valid. After compaction, lost context or a material invalidation, force one fresh recall.
4. `context_incomplete` or `candidate_limit_reached` means relevant constraints may be missing. Narrow the query or batch only relevant `remaining_ids` with `show --scope ... --ids ID ... --current` (up to 8 current records/12000 characters). Full `show --id` also loads audit history and is only needed to inspect provenance. Never claim full context or silently omit an unknown key constraint for speed. Check recalled information against current code and authoritative specifications. Project writes never fall back to global.

## Scope and truth

- `global`: developer work habits and preferences. Explicit cross-project preferences are hard/confirmed rules. Repeated, de-identified feedback may first be stored as a soft candidate; only two distinct task signals from direct user feedback promote it to an active soft preference. Never store business content globally.
- `project`: business, architecture, interfaces, technical constraints, decisions, defects, and lessons for the owning project. Project-outside-CWD discussions still belong to that project. Unbound business stays in the conversation, never global.
- `task`: temporary requirements, progress, blockers and next steps in the owning project's store. Split mixed statements and their evidence by scope. Failed project writes never fall back to global.
- Distinguish `desired`, `observed`, `preference`, and `hypothesis`. Use actual visible user messages, code or tool results as sources. AI restatements and recall hits are not new user evidence. Do not invent message IDs. A successful test can be recorded only from its actual tool result with command, time and code version; intended tests are `verification_steps`.

## Capture and correction

### Record reusable habits clearly

Store one reusable behavior per record; split unrelated preferences instead of writing a profile paragraph. A useful habit record answers: **when does it apply, what should the AI do, what should it avoid, and what exception changes that behavior?** Put those parts in `conditions`, `do`, `dont` and `exceptions`; keep `content` a short, actionable statement. Use a specific title, actual evidence, and one primary topic tag from `analysis`, `implementation`, `debugging`, `verification`, `delivery`, `communication` or `correction`, plus at most two useful subtopic tags. Prefer established subtopic tags; introduce one only when none fits. Tags aid retrieval, but searchable title/body terms remain essential so a wrong or missing tag cannot hide the rule. Do not create empty categories or tag general programming knowledge as a personal habit.

For global learning, record only a de-identified behavior signal visible in the user's request, correction, decision or choice. Keep the source excerpt short and generic. Never infer a private thought or copy project names, business details, code, paths, customer data, raw dialogue or logs into global fields. An explicit cross-project rule can be used immediately. A repeated signal is a candidate until the program sees two distinct task references; do not use or describe a candidate as an established preference before promotion. Similarity of subject, repeated AI wording, or another task in the same work effort is not independent evidence.

### Ordinary apply contract

For ordinary ADD, CHECKPOINT and USE, this section is sufficient; do not read the full advanced protocol just to submit a normal turn. All content-writing operations require a nested **`record` object**; never flatten CHECKPOINT fields onto the operation. Task identity belongs on the envelope. The following shows only the shape; replace every placeholder with actual work and do not save the example:

```json
{"schema_version":1,"scope":"global","session_id":"local-session","turn_id":"local-turn","task_id":"opaque-current-task","idempotency_key":"unique-batch-key","operations":[{"op":"ADD","scope":"global","record":{"kind":"preference","claim_type":"preference","status":"active","strength":"hard","cross_project_confirmed":true,"title":"Check existing code before adding an abstraction","content":"For code changes, inspect and reuse the existing implementation before introducing a parallel abstraction.","conditions":"When changing code in an existing project.","exceptions":"Follow a specific current request to introduce a new abstraction.","do":"Trace existing behavior and reuse suitable code.","dont":"Do not add a competing implementation before checking reuse options.","tags":["implementation","code-reuse"],"source":{"type":"user_statement","excerpt":"Generic, brief evidence of the user's cross-project preference."}}}]}
```

Supported kinds are `business_rule|project_fact|decision|lesson|procedure|preference|convention|checkpoint|summary`; never invent `requirement` as a kind. Claim types are `desired|observed|preference|hypothesis`, strengths `hard|soft|informational`. A checkpoint is optional and describes progress only; it never substitutes for a requirement or decision. New setups use `developer-first`: recall existing project rules, but project/task writes are off until the user runs `dev-memory mode full-project --project-root <path>`. Global habits remain available. Existing settings are not rewritten by setup.

Global explicit habits use `cross_project_confirmed:true`, a global kind and actual user evidence. Inferred habits use only a generic, de-identified candidate with `kind:"preference"`, `claim_type:"preference"`, `strength:"soft"`, `status:"candidate"`, `cross_project_confirmed:false`, and `source.type:"user_feedback"`. Include a generic source excerpt, no project/task names, code, paths, business entities, customer data, raw dialogue or logs, and pass the current opaque `task_id` in the envelope. The store hashes that ID and retains no raw task ID in global evidence. Exact repeats within one task do not count twice. The program promotes a candidate after feedback from two distinct task IDs. Do not actively apply a candidate before promotion; an active soft preference always yields to the current request. A one-time instruction (for example, “skip tests this time”) stays task-local and is never a habit candidate.

Project and global operations may share one envelope with `scope:"both"` and explicit owning scope per operation. Project content never falls back to global. A user-level Codex activation authorizes global habit learning, not project memory.

`model_inference` cannot be active. Actual user sources are `user_statement|user_confirmation|user_feedback`; inspected code uses `code_observation`, executed commands/tests use `tool_result`. Planned checks belong in `verification_steps`; actual passed-test claims require the real tool result. Summaries, optional verified metadata and other advanced operations require the full protocol. Make one bounded save attempt for an explicit correction **before changing affected code**; if storage fails, report it and work from the current explicit instruction without claiming persistence.

Do not call `apply` just to report that nothing changed. A concrete USE can share the existing end-of-turn batch; it needs `id`, current `expected_revision`, `reason` and `action_ref`, and adds no evidence or verification. Its action notes are returned now, but stored receipts keep only ID/revision/reporting metadata. Supply JSON using a quoted heredoc on POSIX (`apply <<'JSON'`, JSON, then `JSON` on its own line), a single-quoted here-string in PowerShell, or `--input` with a scope-local JSON file on any platform. Running `apply` without JSON saves nothing. Inspect every store result. A failed store batch rolls back all its operations and revision changes; another store may have committed successfully. Replays reuse a key only for identical requests; one bounded repair may use a new key and the unchanged source revisions after rollback. No endless retries or false saved claims.

Before edits, connect the applicable recalled `conditions`, `exceptions`, `do`, `dont` and `verification_steps` to the actual design/code decision and its check. Use current user instructions and authoritative code to resolve scope/version conflicts. `unloaded_candidates` is a bounded directory, not loaded rules: fetch the relevant missing IDs with batch `show --current` before acting on an unknown critical constraint; do not fetch every unrelated candidate. Source/code references help target the check, but neither references nor recall prove verification. Across requirements, schema/API, implementation, integration, tests and bug fixes, apply the same canonical rule at the affected layer; phase changes alone add no evidence or duplicate body.

If a rule actually informed an action, optionally include a short `USE` operation in the existing turn's apply batch: current ID/revision, concrete reason and action reference. Never make an extra call just to report use or report every retrieved rule as used. It is an AI report, not proof of execution, a new memory or user evidence. Global use references must stay generic (for example `response-order`); project-specific action references stay project-local.

1. During normal work, notice only new user requirements, corrections, technical choices and observed work preferences. Do not summarize each tool call or start a separate model pass. Save an explicit, important habit correction promptly before affected work; batch ordinary new candidate signals at task end. If nothing new happened, write nothing.
2. Compare with already recalled rules first. Use read-only `match` before `ADD` when context cannot establish equivalence or absence; `empty_store:true` needs no duplicate lookup, but zero hits alone do not establish an empty store. Exact content deduplicates in the program. For paraphrase reuse, revisions, verification, derived summaries or maintenance, read the relevant [advanced protocol](references/protocol.md) once and reuse it until context/version changes. Equivalent paraphrases use `ADD duplicate_of` with current revision and preserved protected fields. Similar titles alone never establish equivalence. Only an independent actual source adds evidence; AI repetition is NOOP. Save explicit corrections promptly; batch ordinary increments at turn end and inspect per-store receipts.
3. For a correction, inspect the existing rule and revise it with `expected_revision`. Preserve old misunderstanding, exact conditions, exceptions, negative requirements, prevention check, and verification method. If a known rule was violated again, investigate missed recall, missed execution or expiry; mark unknown causes unknown. Do not append duplicate rules.
4. Do not call `apply` just to write a NOOP. Save explicit habit corrections promptly; batch ordinary candidates at task end only when there is genuinely new user evidence. Reuse current recall and do not re-read it on each tool call.
5. Task `CHECKPOINT` is opt-in: save it only when the user asks to preserve a continuation point or a meaningful interruption makes it useful. Never create one every turn or turn an intention into completed progress. Existing checkpoint replacement remains atomic and auditable.
6. Maintenance is queued by real changes (normally five pending records or one long record), not by a timer. It is cleanup, not a prerequisite for coding. Do not review a pack during active implementation, trigger another maintenance poll, or force a below-threshold sweep on an ordinary turn. At a natural task boundary, review at most one already-returned bounded topic (8 records/12000 characters per store); fold it into the same end-of-task apply batch as pending habit capture where possible. Otherwise leave it queued for a later quiet boundary. Never delay a user-facing result for cleanup. Compare source and revision history: merge only equivalent rules, revise confirmed corrections, archive only explicitly expired or contradicted rules, and compact only without losing conditions, exceptions, negations or version constraints. Correct topic tags when clearly wrong, while retaining searchable wording. These are AI semantic judgments, not program-verified facts. Read [the maintenance protocol](references/protocol.md) only when a pack is actually being reviewed.
7. Startup `context` checks pending history; do not repeat `maintain` just to poll. If a due topic was reviewed, submit one bounded maintenance batch at the natural task boundary, with its exact `record_scope`, task ID and expected revisions; include `MAINTENANCE_REVIEW` only for fully inspected current revisions. One store may be maintained per bounded pack; `pending_next_turn` means defer. Current correction capture takes priority over cleanup. Disabled, read-only and opt-out controls stop writes. No loop, full-library sweep, automatic export, separate summarizer or cleanup-only work during active coding. Upgrade may queue existing active records once; the queue is database maintenance state, not a request to summarize the full history.
8. Across development phases, reuse a stable task ID and topic tag, with optional `stage:requirements|schema|api|implementation|integration|testing|bugfix` and `module:...` tags. These are retrieval aids, not a mandatory development workflow. Preserve business rules through phase changes; link decisions to actual contracts/code references. Keep desired requirements, implemented behavior, test plans and actual test results distinct. A bug fix records the observed defect, evidence-supported cause (or unknown), regression check and actual verification. Do not copy entire specifications, schemas, logs or source files into memory. Checkpoint only changed progress; no full task retelling each turn.
9. Same-scope derived summaries still require freshly loaded atomic sources and `expected_source_revisions`. Source changes invalidate dependent summaries. Do not create a summary and then archive its sources: that invalidates the summary. Semantic merges keep one canonical atomic rule and superseded provenance history; they do not inflate evidence or cross-project scope.

## User controls and privacy

- A user opting out of this turn requires `skip --session-id ... --turn-id ...` in the applicable scope immediately; it stores opaque IDs only and prevents same-turn reprocessing. Use stable locally generated opaque IDs when the host exposes none, labelled as local IDs. Do not claim successful suppression if skip fails. Do not later ingest content from paused or opted-out turns under new IDs.
- `capture off` pauses writes and keeps recall; `capture disable` disables both. User-requested read-only recall uses `recall --readonly` and performs no initialization/capture. `list`/`show` inspect records; `ARCHIVE` retains history; `forget preview` then user-confirmed `forget apply` deletes managed content. Check cleanup warnings; deletion is not secure disk erasure.
- Never persist credentials, passwords, Cookies, full sensitive logs, unnecessary customer data, or unrelated personal profiles. Deterministic credential checks are incomplete; perform semantic minimization before submitting, including evidence and metadata.
- Markdown is an on-demand reading view of SQLite, never an authoritative write interface. No default telemetry, paid summarizer, vector service or daemon. Cloud model use is not fully offline; local stores have no default application encryption.

## Host boundaries

Project-guided and user-guided modes depend on the host loading the instruction file and the model following it; neither is an enforced event loop. New sessions should make one bounded initial recall, apply relevant habits as the task evolves, then reuse them until task/topic/store context changes. Do not read the full profile, add classification/rating/summarization model calls, or run deep maintenance during ordinary coding. Ordinary uninitialized Skill invocation is base mode. Codex optional hooks remain separate and require explicit configuration and trust. Never assume portable host events. See [Codex adapter](references/codex-hooks.md) and [verification limits](references/verification.md).
